ClearSeal

A security standard for the servers that let AI agents act on real systems.

Scotty, ClearForge LLC · Version 0.8 · CC BY 4.0

The problem, in plain terms

AI assistants increasingly act on real systems through MCP servers — small programs that hand a model a set of tools: read a file, send a message, run a command. The model decides which tool to use by reading each tool's description, which means a tool description is effectively an instruction to the model.

The protocol handles who is calling: its 2026-07-28 revision made OAuth 2.1 and audience-bound tokens mandatory. It does not answer the questions that come next:

  • Is this tool the one someone actually reviewed, or has its description changed since?
  • How far can this tool reach — and is that bound itself protected, or just described?
  • When a message claims to come from your own infrastructure, did it?

ClearSeal is the layer that answers them, built on top of the protocol's own security rather than re-inventing it.

One discipline

Sign → verify against a pinned reference → fail closed, at an off‑box gate.

Applied to every artifact that enters a model's context or crosses between servers. “Pinned” means an approved copy is fingerprinted, and anything that no longer matches the fingerprint is treated as an incident. “Fail closed” means that when verification can't succeed, the answer is no.

What it adds

  • Tool-definition pinning. Every tool description is fingerprinted when it is approved and re-checked every time it loads; a change nobody approved raises an alert. It stops tool poisoning and silent swaps, and the standard ranks it as the highest security-per-effort control it contains.
  • A four-rung danger ladder. Every tool is classed read_only, owned_state, state_change or arbitrary_exec. A tool that faces untrusted input and can change things needs a human confirmation or proven containment — the “Rule of Two.”
  • Pin everything a gate reads. If a security check decides on a property the fingerprint doesn't cover, that property can be flipped and nothing goes red. The standard fixes the tool definition at ten fingerprinted fields and requires a test that fails when a gate reads anything outside them.
  • Containment that travels. On platforms where network isolation isn't possible, a tool declares the exact set of places it may reach. The set itself is fingerprinted, so widening a tool's reach is detectable by construction.
  • Signed messages from the infrastructure. Status alerts and reports sent to the operator are signed and checked against who may speak on that channel and what a message may ask for. A valid signature proves who spoke; it does not grant permission.
  • An audit procedure. A nine-step review for any MCP server — inventory, exposure, classification, vulnerability pass, and a sweep for security decisions that rest on unprotected inputs — ending in a split between fix-now problems and structural refactors.

What it is not

ClearSeal is an integrity and authenticity control. It proves what an artifact is, who produced it, over which channel, how recently, and with what capability. It never proves intent — so it is not a prompt-injection defense, and the standard names believing otherwise as its primary failure mode.

Proving an action is authentic is not the same as making it safe. Safety comes from narrow tool scopes and limits on where tools can reach. In the standard's own words: signing without scoping is a well-authenticated way to get owned.

How it was built

I authored ClearSeal as its owner — deciding and approving every change — with Claude (Anthropic) as executor, drafting and auditing. It was hardened by building against it. Most of what is in versions 0.6 through 0.8 was found by a builder agent implementing the standard and fed back upstream. The design history keeps the lessons:

  • Don't re-derive what the protocol now mandates. When MCP made OAuth mandatory, the standard dropped its own auth design and required conformance instead.
  • Unpinned authority. The same bug was fixed three times in one day before it was recognised as one bug: a security gate deciding on an input the integrity system didn't cover. A new rule now gets swept against every existing gate, not just the one that prompted it.
  • The feedback path is part of the standard. A mechanism invented while building the reference implementation reached the standard seven days late. A fix that isn't fed back is a fix the next builder re-invents — and nobody audits the second version.

Status: version 0.8, investigation phase, in production in one reference implementation. This is the public edition: deployment-specific details are omitted, and section numbers match the full standard so citations resolve in either.

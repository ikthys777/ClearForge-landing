Field notes from building production infrastructure with AI agents. One failure, one rule.

Why publish failures

Almost nobody publishes their failure trail. Writeups describe the system that worked, which teaches you what to build and nothing about what to distrust. So the same handful of mistakes get rediscovered, independently, over and over.

ClearProof is the other half. Every note is a real incident from building a hardened infrastructure stack with AI agents as the builders and a human approving every merge. Each one is sanitised, reproduced, and reduced to a single rule you can apply to a system that looks nothing like mine.

If you read three

  • A Flag Is Not a Control

    A security setting that looked like the boundary and wasn't — the real limit sat three files away, unreviewed. Ends with a three-question test you can run on your own system today.

  • The Alarm Path Is the Least-Tested Code You Have

    A backup monitor whose failure alert had never once worked, from the day it shipped. It passed two independent reviews.

  • A Goal Must End Where the Agent's Authority Ends

    What happens when an AI agent is given a goal that only a human is allowed to finish: it keeps trying, indefinitely. About instructing agents, not about code.

The pattern underneath

The failure that keeps recurring is one bug wearing different clothes: a check that reported success while measuring the wrong thing.

A command meant to find a running process that matched its own command line. A fingerprint that turned out to be the hash of empty input, so a before-and-after comparison “matched” while measuring nothing. Two independent checks that agreed with each other and were both wrong. None of these was a bug in the thing being tested. Every one was a bug in the instrument — and every one looked authoritative until something unrelated contradicted it.

A quieter second class sits beside it: a check fires on a wrong value, and nothing fires on a missing one. Every assertion you write is about something that exists, which is why absence is the failure a test suite is structurally blind to.

Why AI agents make it sharper

An agent writes the code and the check that validates it. Both come from the same understanding of the problem, so if that understanding has a hole, the hole is in both. Agreement between an agent's work and an agent's verification of it is not independent evidence — it is the same reasoning, twice.

That is not an argument against agents. It is an argument for one question, asked by a human, about every green result:

What would make this report success while being wrong?

The rules so far

Systems how programs, controls and checks fail

NoteThe rule
Liveness Is Not IdentityA port answering proves something is there. It does not prove it's the thing you deployed.
A Flag Is Not a ControlA flag that says an exposure exists is not a control. The thing that bounds it is — and it must be inside the hash.
Make the Instrument Disagree With ItselfBefore you trust a probe, feed it something it must reject. If it answers the same to both, it has told you nothing.
Absence Needs Its Own ClockA detector for “nothing happened” cannot be driven by the thing that stopped happening.
The File Nobody Owns Is the One Everybody ReadsThe more often a file is read automatically, the less often it is read deliberately. Audit those first.
An Absence Has No SymptomA check fires on a wrong value. Nothing fires on a missing one.
The Guard Sits Behind Its Own ExitCode written for a condition must be reachable in that condition. Presence is not execution.
The Mutation That Didn't HappenAssert the change took effect before you interpret the outcome. A change that matched nothing succeeds silently.
The Gate That Verifies Against the DefectWhen a ruling forbids a source, every check that consumed it is now suspect — including the ones enforcing the ruling.
The Artifact That Rotted in PlaceAn open change decays against a moving base. Staleness is measured in merges, not days.
The Tip That Advertised Its ScaffoldNever leave a live pull-request tip on placeholder content. Push atomic restores only.
The Failure That Heals Its Own SymptomA recovery path must not clear an alarm it cannot verify. A half-done state needs a name of its own.
Name What Your Test Stood In ForA substitute is most convincing as it approaches the real thing — and the closer it gets, the less anyone re-checks it.
The Alarm Path Is the Least-Tested Code You HaveCode that runs only when something is already wrong is the least-exercised and most consequential code you own.

Orchestration how instructing an agent fails

NoteThe rule
A Goal Must End Where the Agent's Authority EndsA goal only reachable through an action the agent is forbidden to take can never be met — and a completion loop will pursue it indefinitely.

The list grows as the work does. A note is added when a new failure teaches something the existing rules don't already cover.

The repo holds itself to its own rules

A sanitisation gate runs on every change. It scans the current files and every line ever added in the history — because a secret committed once and removed in the next commit is public forever.

Before its result is believed, the gate runs a self-test: it fires every rule against a deliberately bad sample and confirms each one goes red. A gate nobody has watched fail is indistinguishable from a gate that cannot.
